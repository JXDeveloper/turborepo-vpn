System design draft

VPN Control Plane and Managed Peer Provisioning Flow

The Control Panel links a Clerk-authenticated subscriber to a WireGuard peer running on an Exit Node. It owns the durable record of who a peer belongs to and whether their subscription entitles them to service; the Exit Node remains the sole authority over the live WireGuard interface. Neon (Postgres) accessed through Drizzle ORM is the system of record for users, subscriptions, exit nodes, and peers.

Browser -> Control Panel: Clerk session Control Panel -> Neon: Drizzle queries Control Panel -> Exit Node: service-to-service API key Peer -> Exit Node: WireGuard handshake (UDP)

Entities

Five entities compose the system. Ownership is split so that no single component can both grant service and collect payment.

  • User — identity and session, managed entirely by Clerk.
  • Subscription — billing state and plan entitlement, managed by Clerk (or a billing provider behind it), mirrored into Neon for fast local checks.
  • Control Panel — the application server. Orchestrates peer creation, owns the Neon database via Drizzle, and is the only component with credentials to call Exit Nodes.
  • Exit Node — a WireGuard gateway host. Exposes a small internal HTTP API for peer lifecycle operations and nothing else public-facing except the WireGuard UDP port.
  • Peer — the client device's tunnel identity: a WireGuard keypair, an assigned tunnel IP, and the routing/DNS parameters it needs to connect.

Trust Boundaries

A signed-in user is not, by itself, a provisioned peer. Reaching an active tunnel requires all of the following:

  • a Clerk-authenticated session for a real user;
  • a subscription row in Neon whose status is active as of the request;
  • a peer row owned by that user, created by the Control Panel;
  • the corresponding peer entry actually present in the Exit Node's live WireGuard configuration; and
  • possession of the private key and config, which only ever leaves the Control Panel once, at creation time.
The Exit Node never talks to Clerk or Neon directly. It only accepts authenticated calls from the Control Panel and only ever learns a public key, never a user identity.

Data Model (Drizzle / Neon)

Table Key columns Notes
users id, clerk_user_id, email, created_at Mirrors just enough Clerk identity to join against locally; Clerk remains the source of truth for auth.
subscriptions id, user_id, clerk_subscription_id, plan, status, current_period_end, revoked_at status is the fast local check (active, past_due, revoked) kept in sync by the Clerk webhook.
exit_nodes id, region, hostname, api_base_url, public_key, capacity One row per WireGuard gateway host; the Control Panel picks a node when a peer is created, e.g. by region or current load.
peers id, user_id, exit_node_id, public_key, private_key_encrypted, assigned_ip, status, created_at, revoked_at The private key is generated once by the Control Panel, encrypted at rest, and only ever decrypted to re-render a config or QR code for its owner.
Storing the private key at all is a deliberate trade-off for convenience (letting a user re-open their QR code later without re-provisioning). If that risk is unacceptable, the Control Panel can instead show the config once and store only the public key, forcing re-creation of the peer if the user loses their device config.

Flow 1: First-Time User — Sign-Up Through First Peer

sequenceDiagram
  participant U as New user
  participant B as Browser
  participant Clerk as Clerk
  participant CP as Control Panel
  participant DB as Neon (Drizzle)
  participant EN as Exit Node

  U->>B: Visit application
  B->>Clerk: Sign in / sign up
  Clerk-->>B: Session established
  B->>CP: Land on landing page
  U->>B: Click "View pricing"
  B->>Clerk: Select plan and complete checkout
  Clerk-->>CP: subscription.created webhook
  CP->>DB: Upsert subscriptions row (status = active)
  Clerk-->>B: Redirect to home
  U->>B: Click "Dashboard"
  B->>CP: GET /dashboard/home
  CP->>DB: Load user + subscription status
  CP-->>B: Render dashboard with "Create peer" button
  U->>B: Click "Create peer"
  B->>CP: POST /api/peers
  CP->>CP: Generate WireGuard keypair, pick exit node
  CP->>DB: Insert peers row (status = pending)
  DB-->>CP: Row committed
  CP->>EN: POST /peers (public_key, assigned_ip candidate)
  EN->>EN: Add peer to wg0, allocate tunnel IP
  EN-->>CP: Peer config fields (server pubkey, endpoint, allowed IPs)
  CP->>DB: Update peers row (status = active, assigned_ip)
  CP-->>B: Full client config + QR code
  U->>B: Scan QR in WireGuard app
  B-->>EN: WireGuard handshake, tunnel established
The Neon row is written and committed before the Exit Node is asked to create anything, so a crash between steps leaves an orphaned "pending" database row rather than an orphaned live peer with no record of its owner.

If the Exit Node call fails or times out, the Control Panel should retry idempotently (keyed on the peer id) rather than generating a second keypair, and should surface a clear retry state on the dashboard instead of a half-provisioned peer.

Flow 2: Returning User With Subscription Remaining

sequenceDiagram
  participant U as Returning user
  participant B as Browser
  participant Clerk as Clerk
  participant CP as Control Panel
  participant DB as Neon (Drizzle)
  participant EN as Exit Node

  U->>B: Sign in
  B->>Clerk: Authenticate
  Clerk-->>B: Session established
  B->>CP: GET /dashboard/home
  CP->>Clerk: Verify session
  CP->>DB: Read subscription status for user
  alt status = active
    CP->>DB: Load existing peers for user
    CP->>EN: GET /peers/:id (optional live status check)
    EN-->>CP: Peer status, last handshake time
    CP-->>B: Render existing peer(s), config, and QR on demand
  end

The QR code and config are regenerated from the stored, encrypted private key rather than re-provisioned, so re-scanning does not create a second peer or invalidate the first one on the Exit Node.

Flow 3: Returning User Without Subscription Remaining

Subscription check fails Control Panel reads subscriptions.status as past_due or revoked for the user.
Dashboard shows entitlement message The dashboard renders "You have no subscription left" with a link back to the pricing page, instead of the peer list or create-peer button.
No Exit Node call is made The Control Panel never queries or contacts the Exit Node on this path; an unentitled user's request stops entirely at the database check.

Flow 4: Subscription Revocation

sequenceDiagram
  participant Clerk as Clerk
  participant CP as Control Panel
  participant DB as Neon (Drizzle)
  participant EN as Exit Node

  Clerk->>CP: POST /webhooks/clerk (subscription.deleted, signed)
  CP->>CP: Verify webhook signature
  CP->>DB: Set subscriptions.status = revoked, revoked_at = now()
  CP->>DB: Load all active peers for the affected user
  loop for each active peer
    CP->>EN: POST /peers/:id/revoke
    EN->>EN: Remove peer from wg0 immediately
    EN-->>CP: Ack
    CP->>DB: Set peers.status = revoked, revoked_at = now()
  end
  CP-->>Clerk: 200 OK
The webhook handler must verify the Clerk signature before trusting the payload, and the revoke loop should be retried on failure so a temporarily unreachable Exit Node cannot leave a cancelled subscriber connected indefinitely.

Control Panel HTTP API

Endpoint Authentication Purpose
GET /dashboard/home Clerk session Load subscription status and existing peers for the signed-in user.
POST /api/peers Clerk session, active subscription required Generate a keypair, persist the peer, and provision it on the selected Exit Node.
GET /api/peers/:id/config Clerk session, peer owned by requester Re-render the stored config and QR code without contacting the Exit Node.
POST /webhooks/clerk Clerk webhook signing secret Receive subscription lifecycle events and drive local status plus Exit Node revocation.

Exit Node Internal API

Endpoint Authentication Purpose
POST /peers Control Panel service API key Add a peer to the wg0 interface, allocate a tunnel IP, return server-side config fields.
GET /peers/:id Control Panel service API key Return live peer status, including last handshake time and bytes transferred.
POST /peers/:id/revoke Control Panel service API key Remove a peer from the wg0 interface immediately, halting service.
The Exit Node API should never be reachable from the public internet; it is called only by the Control Panel over a private network or an allow-listed IP plus API key.

Implementation Checklist

  • Verify the Clerk webhook signature on every incoming event before writing to Neon.
  • Write the peer row to Neon before calling the Exit Node, and make the Exit Node call idempotent on peer id so retries cannot create duplicate peers.
  • Encrypt the stored private key at rest; decrypt only in-memory when re-rendering a config or QR code for its verified owner.
  • Gate POST /api/peers on a fresh subscription status check, not a cached session claim, so a revoked user cannot create a new peer.
  • Make subscription revocation call revoke_peer/:id for every active peer owned by the user, and retry on Exit Node failures rather than dropping the event.
  • Keep the Exit Node's internal API off the public internet; restrict it to the Control Panel's network or IP range plus a service API key.
  • Track peer status (pending, active, revoked) in Neon so the dashboard, not just the Exit Node, has a source of truth for what to display.
